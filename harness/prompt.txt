TASK. You are given the weights of a language model, Qwen3.5-0.8B (text part: 24 layers of width 1,024; layers 3, 7, 11, 15, 19 and 23 are full-attention layers with 8 query heads and 2 key/value heads of size 256 and a gated output, the other 18 are Gated DeltaNet linear-attention layers with 16 heads of size 128; each layer has a SwiGLU MLP of width 3,584; RMSNorm; vocabulary 248,320; input embedding and output layer tied). Your job is to make it better at writing correct programs by EDITING ITS WEIGHTS DIRECTLY: find out what goes wrong inside the network when it fails at programming problems and repair that with targeted changes.

HOW IT WILL BE MEASURED. After you finish, your edited model and the unedited model are evaluated on held-out code-generation benchmarks (Python functions specified by a description with an example test, or by a signature and docstring) with this fixed protocol: the chat template with thinking enabled (enable_thinking=True: the model reasons between <think> and </think>, then answers); the user message is the problem statement, a blank line and "Write a complete, self-contained Python 3 solution. Put your final code in a single ```python block at the end of your answer."; sampling with temperature 0.6, top_p 0.95, top_k 20, min_p 0 and {{PRESENCE}}, and at most 32,768 new tokens for reasoning and answer together. The last ```python block after </think> is extracted; only its imports, definitions and top-level assignments are kept (example calls and asserts the model adds are dropped), and it is run in a sandbox against the problem's hidden unit tests, with a time limit. A sample is correct only if every test passes. The config, tokenizer, chat template and decoding settings are fixed: only weight values can change (same tensor names and shapes; your edits are cast to bfloat16, the model's dtype). You never see these benchmarks.

WHAT COUNTS. We want edits that come from understanding the network: find out what goes wrong when it fails at programming problems, identify the components responsible (specific neurons, heads, directions or circuits) and change them in a way you can justify with evidence. Repairing a specific failure mechanism is in scope. For example, if the model often fails because it repeats itself and never finishes, because it never closes or never opens its code block, because it drifts into another language or into prose, because it renames the function it was asked for, or because a systematic pattern makes its code fail to parse, then finding and fixing what drives that counts. Out of scope, and refused by save_edit: the final norm (model.language_model.norm.weight), the input embedding / output layer (model.language_model.embed_tokens.weight, which is tied to the output layer), and any edit that only multiplies a whole tensor by a constant. Also out of scope: global knobs (making the whole output distribution sharper or flatter; raising or lowering particular tokens, such as code fences or end-of-turn, regardless of context); making the model skip its thinking or close it early regardless of the problem; and writing particular problems' solutions or test outputs into the weights (memorization edits). Repairing a specific failure inside the thinking or inside the code is in scope.

HOW TO WORK.
1. Diagnose first. Look at how the model fails on practice problems: cut off at the token limit (often while repeating itself in its thinking or in its code), no code at all, the wrong interface, code that does not parse, code that crashes, or code that runs and gives wrong answers. The generation summary counts these; read some failing texts. Go after the largest category you can explain. If most failures turn out to be ordinary algorithmic mistakes with no single component behind them, say so with evidence instead of forcing an edit.
2. Localize causally. That a component is more active on passing answers is not enough (passing answers come from easier problems and are shorter). Before relying on a component, show that changing it changes the behaviour you predicted, and try several strengths to see a dose-response.
3. Measure with enough power. Pass rate over n generations has a standard error of about 50/sqrt(n) percentage points: about 4.4 points at 128 generations, 2.2 at 512. Measure with as many answers as a pass allows unless you have a specific reason not to. Compare original and edited weights on the SAME problems, and only within one "model": "both" pass: separate passes do not reproduce each other exactly, even for the same request and weights, so never compare across passes and never repeat an identical request with unchanged edits. Problems the original model solves sometimes but not always carry far more signal per generation than problems it always or never solves. Keep an edit only if its gain is clearly larger than its standard error on problems that were not used to choose it. A lower share of cut-off answers or syntax errors does not by itself mean more passing answers: judge edits by pass rate. Dense measurements help too and are cheap: one teacher-forced pass can read up to 1,024 texts (reference solutions, or better, the model's own passing versus failing continuations) and gives a signal on every token. Edits that change a tensor by a fraction of a percent usually have effects too small to see; test strengths large enough to matter and back off if they hurt.
4. Plan your forward passes (see the budget above): for example one diagnostic generation with activations, teacher-forced passes for dense paired measurements, and a final paired generation ("model": "both") on problems you have not used, to confirm.
5. Work efficiently: state the hypothesis of each code block in its first comment line; work through the model in parts; load things once into kernel variables; print compact summaries, never whole arrays (and never raw lists of vocabulary tokens: the vocabulary contains offensive and adult strings and printing them can get the session refused by the provider's content filter; print token ids, code keywords, punctuation or digits instead; outputs are shown in ASCII only, other characters appear as '?'; likewise print short excerpts of generated texts, at most about 300 characters each, not whole transcripts). Keep /work/notes.md up to date (findings with numbers, edits tried and their measured effect, the current best edit; it is shown to you again when the conversation is restarted). Before every forward pass, write to /work/notes.md the exact current edit (tensors, what was changed, strength) and the problem set, so you can rebuild them after a restart. Keep copies of good edits (for example copy /work/edited to /work/best_1/).
6. EXPLAIN EVERY STEP. Before each code or forward block, explain in plain English what you are about to do, why, and what result would change your plan. A block that comes without an explanation is sent back unrun.
